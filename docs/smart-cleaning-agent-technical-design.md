# 智能扫地机器人客服 Agent 技术设计与架构演进文档

## 1. 项目定位

本项目是一个面向扫地机器人使用场景的智能客服系统，核心目标不是简单做一个聊天窗口，而是把“产品知识问答、实时天气建议、个人使用报告、多轮追问”统一到一个可解释、可扩展的 Agent 架构中。

系统基于 Streamlit 构建前端交互入口，使用 LangChain ReAct Agent 负责工具选择和任务编排，并通过 RAG 检索增强回答的可靠性。项目的设计重点在于：用户可以像咨询客服一样自然提问，系统会根据问题类型自动选择知识库检索、天气查询或用户记录分析等能力，并在多轮对话中尽量保持上下文连续。

本文档记录项目迭代过程中逐步沉淀下来的架构设计、核心链路和关键取舍，重点围绕系统边界、模块职责、数据流转和可维护性展开。

文档的目标是帮助读者理解项目如何将前端交互、Agent 编排、工具调用、RAG 检索和外部数据报告组织成一个完整的智能客服系统。

本文档主要关注以下问题：

- 系统如何通过分层架构拆分 UI、Agent、工具、RAG、数据和配置。
- Agent 如何根据用户问题选择知识库问答、天气查询或报告生成工具。
- RAG 如何通过 FAQ 预处理、查询改写和 rerank 提升检索效果。
- 报告模式如何结合结构化用户记录生成可追溯的回答。
- 项目如何通过配置、日志和测试降低维护成本。

## 2. 总体架构

项目整体可以分为六层：

```text
用户界面层
  app.py
    |
Agent 编排层
  agent/react_agent.py
  agent/conversation_context.py
    |
工具能力层
  agent/tools/agent_tools.py
  agent/tools/middleware.py
    |
RAG 检索生成层
  rag/rag_service.py
  rag/vector_store.py
  rag/preprocess.py
  rag/query_rewrite.py
  rag/rerank.py
    |
模型与配置层
  model/factory.py
  config/*.yml
  prompts/*.txt
    |
数据与评测层
  data/
  chroma_db/
  md5.txt
  tests/
```

这种分层的目的，是让每一层只关心自己的职责：

- UI 层只负责展示、输入、流式输出和启动检查。
- Agent 层只负责判断用户意图、维护对话上下文、决定是否进入报告模式。
- 工具层只暴露可被 Agent 调用的能力，比如 RAG、天气、用户记录。
- RAG 层只负责知识库入库、检索、改写、重排和回答生成。
- 模型与配置层统一管理模型实例、路径、提示词和参数。
- 数据与评测层提供知识库、外部记录和测试样例。

## 3. 请求处理主流程

用户从页面输入问题后，请求会按下面流程执行：

```text
用户输入
  -> app.py 接收输入并创建流式响应
  -> ReactAgent.execute_stream()
  -> ConversationContext.resolve_query() 解析多轮上下文
  -> 根据问题判断是否预开启报告模式
  -> LangChain Agent 执行 ReAct 推理
  -> Agent 选择调用工具
      -> rag_summarize / get_weather / fetch_external_data / fill_context_for_report
  -> 中间件记录工具调用、切换报告提示词
  -> 模型生成最终回答
  -> app.py 解析 <thinking>/<final> 标签并流式渲染
```

这个流程的关键设计是：前端并不直接判断所有业务类型，而是把用户问题交给 Agent。Agent 结合工具描述、系统提示词和运行时上下文决定下一步动作，这样后续增加新工具时，不需要重写 UI 主流程。

## 4. UI 层设计

对应文件：`app.py`

UI 层使用 Streamlit 实现，主要职责包括：

- 展示项目首页、示例问题卡片和聊天区域。
- 读取用户输入并把问题传给 `ReactAgent`。
- 使用 `execute_stream()` 实现流式输出。
- 解析模型输出中的 `<thinking>` 和 `<final>` 标签，把思考过程和最终结果分开展示。
- 显示 RAG 参考来源和报告模式结果。
- 在侧边栏展示当前绑定用户、城市、默认月份、可查询月份和启动提醒。

这里的设计重点是 UI 层保持轻量。它不直接做 RAG 检索、不直接拼报告、不直接调用天气 API，而是把复杂逻辑交给 Agent 和工具层。这样页面逻辑更清晰，也方便后续替换前端框架。

## 5. Agent 编排层设计

对应文件：

- `agent/react_agent.py`
- `agent/conversation_context.py`

### 5.1 ReAct Agent

`ReactAgent` 是系统的核心编排器。它基于 LangChain 的 `create_agent` 创建 Agent，并注册以下工具：

- `rag_summarize`：知识库问答。
- `get_weather`：查询实时天气。
- `get_user_location`：获取当前绑定城市。
- `get_user_id`：获取当前绑定用户 ID。
- `get_current_month`：获取当前月份。
- `fetch_external_data`：读取用户月度使用记录。
- `fill_context_for_report`：触发报告模式上下文注入。

Agent 层的价值在于它不把所有能力写成 if/else，而是把能力包装为工具，让模型根据用户问题选择调用路径。例如：

- 用户问“滤网多久清理一次”，Agent 会调用 RAG 工具。
- 用户问“东莞今天适合拖地吗”，Agent 会调用天气工具。
- 用户问“生成我本月的使用报告”，Agent 会调用用户 ID、当前月份、外部记录等工具，并切换到报告提示词。

### 5.2 报告模式路由

报告相关逻辑不是完全依赖模型自由判断，而是在 `ReactAgent` 中加入了关键词预判：

- 强触发词：生成报告、使用报告、本月报告、月度报告等。
- 弱触发词：生成、查看、总结 + 报告、月报、使用情况。
- 追问触发词：上个月、上上个月、相比、对比、耗材、清洁效率等。

这样做的原因是报告场景对输出格式要求更高，而且需要调用用户外部记录。如果完全交给模型判断，可能出现工具调用不稳定或提示词未切换的问题。因此项目采用“规则预判 + Agent 工具调用”的混合方案，在可控性和灵活性之间做平衡。

### 5.3 多轮对话上下文

`ConversationContext` 负责处理用户追问。它维护最近若干轮对话，并提取两类上下文：

- 话题上下文：比如滤网、主刷、故障排查、维护保养、报告等。
- 会话事实：比如家里有宠物、木地板、地毯、老人使用、自动集尘等。

当用户后续问“那这个多久清理一次？”时，系统会尝试把问题补全为更完整的检索查询，而不是直接拿短句去检索。这样可以提升多轮对话的命中率。

同时，它也设置了话题切换保护。比如用户从“滤网清理”突然问“天气怎么样”，系统不会错误继承上一个 RAG 话题，避免上下文污染。

## 6. 工具能力层设计

对应文件：

- `agent/tools/agent_tools.py`
- `agent/tools/middleware.py`

工具层把外部能力统一封装成 LangChain Tool，供 Agent 调用。

### 6.1 RAG 工具

`rag_summarize(query)` 会懒加载 `RagSummarizeService`，执行知识库检索和答案生成，并把本次命中的来源保存到运行时状态 `runtime_state["last_rag_sources"]`。这样 UI 层可以在最终回答后展示参考来源。

### 6.2 天气工具

天气工具使用 Open-Meteo 的地理编码和天气接口：

- 先把城市名转换为经纬度。
- 再查询温度、湿度、天气代码、风速和降水概率。
- 最后格式化为中文天气描述，交给 Agent 结合扫拖建议生成回答。

这个设计避免项目依赖收费天气服务，也不需要额外 API Key。

### 6.3 外部用户记录工具

用户记录来自 `data/external/records.csv`。工具层会读取用户 ID、月份、清洁效率、耗材状态和对比信息。

外部数据设计中加入了几个保护：

- 用户 ID 必须来自环境变量 `AGENT_USER_ID`，不能让模型随机编造。
- 城市来自环境变量 `AGENT_USER_CITY`。
- 如果当前月份没有记录，会自动回退到最近可用月份。
- 如果用户 ID 不存在，会返回明确错误提示。

这让报告生成更像真实业务系统：模型负责表达和总结，数据来源由工具层控制。

### 6.4 中间件设计

`middleware.py` 使用 LangChain middleware 做三件事：

- `monitor_tool`：记录工具调用名称、参数和结果状态。
- `log_before_model`：模型调用前记录消息数量和报告模式状态。
- `report_prompt_switch`：根据运行时上下文动态切换普通提示词或报告提示词。

这里的设计亮点是把“报告提示词切换”放在中间件，而不是散落在业务代码里。这样 Agent 执行链路更统一，报告模式也更容易维护。

## 7. RAG 检索生成层设计

对应文件：

- `rag/vector_store.py`
- `rag/rag_service.py`
- `rag/preprocess.py`
- `rag/query_rewrite.py`
- `rag/rerank.py`
- `rag/evaluate_retrieval.py`

RAG 层是项目中最能体现工程设计的部分。它不是简单把文档切块后丢进向量库，而是加入了面向 FAQ 文档的预处理、查询改写、候选召回、重排和来源追踪。

### 7.1 文档入库流程

`VectorStoreService.load_document()` 的入库流程如下：

```text
读取 data/ 下允许类型文件
  -> 支持 txt 和 pdf
  -> 计算文件 MD5
  -> 如果 md5.txt 中已存在该 MD5，则跳过
  -> 加载原始文档
  -> prepare_documents() 清洗和结构化切分
  -> 写入 Chroma 向量库
  -> 保存 MD5，避免重复入库
```

这里使用 `md5.txt` 做增量入库去重，解决的问题是：每次运行入库脚本时，不重复写入已经处理过的知识文件，避免向量库中出现重复 chunk。

需要注意的是，`reset_db=True` 会删除 Chroma 持久化目录。如果要做真正的全量重建，也需要同步处理 `md5.txt`，否则可能出现向量库已删除，但 MD5 记录仍认为文件已入库，导致文档被跳过。因此，向量库重建流程中需要把 Chroma 持久化数据和 MD5 去重记录作为一组状态来设计。

### 7.2 FAQ 预处理

`rag/preprocess.py` 负责把原始文档变成更适合检索的 chunk。

主要处理逻辑：

- 统一换行、空格和多余空行。
- 识别 FAQ 格式中的问题和答案。
- 将 FAQ 转换为结构化文本：`问题: ... 答案: ...`
- 在 metadata 中保存 `chunk_type`、`section_title` 和 `question`。
- 如果不是 FAQ 文档，则使用 `RecursiveCharacterTextSplitter` 做普通文本切分。

这样做的好处是：扫地机器人知识文档往往是“问题-答案”形式，如果直接按固定长度切块，问题和答案可能被切散。FAQ 预处理可以保留问答结构，让检索更容易命中完整答案。

### 7.3 查询改写

`rag/query_rewrite.py` 使用规则改写用户问题。它不是调用大模型改写，而是用领域词表做轻量增强。

例如：

- 用户说“不出水”，扩展为水箱、出水管、出水量、拖布等词。
- 用户说“吸力变弱”，扩展为尘盒、滤网、风道、主刷等词。
- 用户说“宠物”，扩展为毛发、防缠绕、滤网、主刷等词。

这种规则改写的优点是稳定、可解释、成本低，也便于在调试检索效果时定位问题。

### 7.4 候选召回和重排

`VectorStoreService.search()` 会根据配置决定走普通检索还是增强检索。

增强检索流程：

```text
原始 query 检索候选文档
  -> 如果改写 query 不同，再用改写 query 检索一次
  -> 合并并去重候选文档
  -> rerank_documents_with_source_diversity()
  -> 返回 top-k 文档
```

`rag/rerank.py` 的重排逻辑会综合考虑：

- 原始 query token 在文档中的命中。
- 扩展词在文档中的命中。
- query token 在 FAQ 问题字段中的命中。
- 扩展词在 FAQ 问题字段中的命中。
- FAQ chunk 额外加权。
- 来源多样性，避免 top-k 全部来自同一个文件。

这使得检索结果不仅依赖向量相似度，也结合了扫地机器人场景中的关键词和 FAQ 结构。

### 7.5 检索后生成

`RagSummarizeService` 负责把检索到的文档组织成上下文，然后调用大模型生成回答。

它的核心职责是：

- 调用 `vector_store.search(query)` 获取相关文档。
- 从 metadata 中提取来源文件名。
- 构造包含参考资料和元数据的上下文。
- 使用 `prompts/rag_summarize.txt` 对答案进行约束。
- 如果没有检索到内容，返回明确的兜底提示，避免模型编造答案。

## 8. 模型与配置层设计

对应文件：

- `model/factory.py`
- `config/rag.yml`
- `config/chroma.yml`
- `config/agent.yml`
- `config/prompts.yml`
- `utils/config_handler.py`
- `utils/prompt_loader.py`

项目把模型、向量库、上下文窗口、提示词路径等都放到配置文件中，而不是硬编码在业务逻辑里。

主要配置包括：

- `config/rag.yml`：聊天模型和 embedding 模型名称。
- `config/chroma.yml`：Chroma collection、持久化路径、chunk 大小、top-k、查询改写和 rerank 开关。
- `config/agent.yml`：外部数据路径、多轮上下文窗口、session facts、话题切换保护等。
- `config/prompts.yml`：普通提示词、RAG 总结提示词、报告提示词的路径映射。

`model/factory.py` 用工厂类创建 `ChatTongyi` 和 `DashScopeEmbeddings`。这样模型实现集中在一个地方，后续替换模型时不需要改 Agent 和 RAG 主流程。

## 9. 数据设计

### 9.1 知识库数据

知识库文件放在 `data/` 目录下，支持 `.txt` 和 `.pdf`。当前数据覆盖：

- 扫地机器人常见问答。
- 扫拖一体机器人问答。
- 故障排除。
- 维护保养。
- 选购指南。

这些文档经过清洗、FAQ 识别、切片、embedding 后写入 ChromaDB。

### 9.2 外部用户记录

外部记录放在 `data/external/records.csv`，用于生成个人使用报告。

字段设计围绕报告生成需要，包括：

- 用户 ID。
- 时间月份。
- 用户特征。
- 清洁效率。
- 耗材状态。
- 对比信息。

报告模式下，Agent 不直接编造用户情况，而是通过工具读取 CSV 记录，再由报告提示词组织成自然语言报告。

### 9.3 运行时状态

工具层维护 `runtime_state`，用于保存一次 Agent 运行过程中的状态：

- `last_rag_sources`：最近一次 RAG 命中的来源。
- `report_mode`：当前是否处于报告模式。
- `last_external_data`：最近一次报告使用的用户记录。

这些状态让 UI 可以展示来源，也让报告追问可以基于上一次报告上下文做对比。

## 10. 提示词设计

项目把提示词独立放在 `prompts/` 目录，主要包括：

- 普通客服提示词：控制 Agent 的基础人设、工具使用方式和回答风格。
- RAG 总结提示词：要求模型基于参考资料回答，避免脱离知识库发挥。
- 报告生成提示词：要求模型输出结构化月度使用报告。

提示词通过配置文件映射，由 `utils/prompt_loader.py` 加载。报告模式下，中间件会动态切换到报告提示词，这样普通问答和报告生成可以使用不同的行为约束。

## 11. 异常与边界处理

项目中已经考虑了多种异常场景：

- 启动时检查配置文件、知识库路径和外部记录路径是否存在。
- 如果没有配置 `DASHSCOPE_API_KEY`，前端会提示模型调用可能失败。
- 如果用户 ID 或城市环境变量缺失，工具会返回明确提示。
- 如果用户 ID 不在 `records.csv` 中，报告工具会拒绝生成虚假记录。
- 如果目标月份没有记录，会回退到最近可用月份。
- 如果 RAG 没有检索到文档，会返回“知识库暂时没有检索到”的兜底回答。
- 如果工具调用失败，中间件会记录错误日志，方便排查。

这些处理让系统更像一个可运行的工程项目，而不是只在理想输入下工作的 demo。

## 12. 测试与验证

项目包含自动化测试，覆盖核心工程风险：

- `tests/test_agent_tools.py`：验证工具函数和外部数据处理。
- `tests/test_conversation_context.py`：验证多轮上下文、话题继承和话题切换。
- `tests/test_rag_enhancement.py`：验证查询改写、rerank、增强检索等 RAG 逻辑。
- `tests/test_report_routing.py`：验证报告模式触发和追问处理。
- `tests/test_evaluate_retrieval.py`：验证检索评估相关逻辑。
- `tests/test_eval_set_quality.py`：验证评测数据集字段质量。

同时，`data/rag_eval_set.example.json` 提供了带 `query`、`expected_sources`、`category`、`reason` 和 `evidence` 的检索评测样例，用于说明为什么某个问题应该命中特定来源。

从工程验证角度看，这部分可以说明：项目不只是“能跑”，还对关键模块设计了验证方式。

## 13. 关键设计取舍

### 13.1 为什么使用 Agent + Tool

如果所有能力都写成固定 if/else，短期实现简单，但后续扩展会越来越难。例如新增“耗材购买建议”“设备故障工单”“用户画像分析”时，主流程会不断膨胀。

使用 Agent + Tool 后，每个能力可以独立封装，Agent 负责选择工具。这样项目更接近真实智能客服系统的架构。

### 13.2 为什么 RAG 不只做向量检索

扫地机器人知识库里有大量 FAQ 和故障现象。如果只做普通向量检索，可能会遇到：

- 用户说法和文档说法不一致。
- 问题和答案被切在不同 chunk。
- top-k 被同一来源文件占满。
- FAQ 标准答案没有被优先选中。

因此项目加入 FAQ 预处理、查询改写和 rerank，让检索更适合当前领域。

### 13.3 为什么报告模式需要专门路由

报告生成依赖外部用户记录，需要更强的数据约束。如果完全依赖模型判断，可能出现不调用工具、月份错误、用户 ID 编造等问题。

所以项目使用关键词预判、中间件切换提示词、工具层读取 CSV 的组合方案，让报告生成既能自然触发，也能保持数据可控。

### 13.4 为什么配置和提示词外置

模型名称、chunk 大小、top-k、提示词路径、上下文窗口等参数经常需要调试。如果硬编码在代码里，每次修改都要改业务逻辑。

外置配置可以让项目更容易调参，也能向技术读者说明系统具备可维护性。

## 14. 演进预留

在当前架构上，系统保留了以下可演进方向：

- 收敛更完整的全量重建逻辑：`reset_db=True` 时同步清理或重建 `md5.txt`。
- 增加 RAG 召回率、命中率、MRR 等指标输出，让评测更量化。
- 将外部用户记录从 CSV 替换为数据库或 API，模拟真实业务后端。
- 增加工具调用超时和重试策略，提升外部 API 稳定性。
- 增加更细粒度的报告模板，比如周报、月报、耗材专项报告。
- 增加前端管理页，用于上传知识文档、重建向量库和查看检索评测。

## 15. 总结

这个项目的核心价值在于，它不是单纯调用大模型聊天，而是围绕扫地机器人客服场景逐步形成了一套完整的工程链路：

```text
前端交互
  -> Agent 意图编排
  -> Tool 能力调用
  -> RAG 知识增强
  -> 外部数据报告
  -> 多轮上下文追问
  -> 流式结果展示
```

从技术设计角度看，最值得强调的是“分层”和“可解释”。每个模块都有清晰职责，每个关键能力都有对应文件和实现路径，因此这份文档不仅说明系统能完成智能客服功能，也记录了项目在 Agent 编排、RAG 工程化、工具调用和多轮上下文管理上的设计演进。
